# MCP server on Cloudflare: LifeOS Training

*Research snapshot: 2026-10-20. Sources are official MCP and Cloudflare documentation/source only.*

## Verified platform facts

### Protocol and SDK

- The current MCP specification revision is **2026-07-28**. Its Streamable HTTP transport is one MCP endpoint accepting `POST`: each JSON-RPC request is a separate POST, answered with either one JSON object or a request-scoped SSE stream. The revision removed the `GET` stream endpoint and protocol-level sessions. [MCP Streamable HTTP — 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)
- Use the TypeScript SDK v2 server package, **`@modelcontextprotocol/server`**, with `McpServer` and `createMcpHandler`. The official server package manifest currently declares version **2.3.1**; Cloudflare's Agents MCP handler guide demonstrates the v2 path with `@modelcontextprotocol/server@2.0.0` and says to use the version required by the installed Agents release. [MCP SDK v2 HTTP serving](https://ts.sdk.modelcontextprotocol.io/v2/serving/http) · [official server package manifest](https://raw.githubusercontent.com/modelcontextprotocol/typescript-sdk/main/packages/server/package.json) · [Cloudflare MCP handler API, updated 2026-10-18](https://developers.cloudflare.com/agents/model-context-protocol/apis/handler-api/)
- `createMcpHandler` is fetch-native: its factory creates a fresh `McpServer` for every request, while `{ fetch }` mounts directly on Cloudflare Workers. It is therefore compatible with the repository's Web-standard Worker environment without a Node adapter. Do not place request state in the server instance; durable application data belongs in D1 (or another Worker binding). [MCP web-standard runtimes](https://ts.sdk.modelcontextprotocol.io/v2/serving/web-standard) · [Cloudflare Workers fetch handler, updated 2026-04-23](https://developers.cloudflare.com/workers/runtime-apis/handlers/fetch/) · [Cloudflare D1, updated 2026-04-30](https://developers.cloudflare.com/d1/)
- The SDK handler itself does **not** validate `Host`/`Origin` or bearer tokens. On a bare Worker, put `hostHeaderValidationResponse` and `originValidationResponse` ahead of `handler.fetch`, verify the token, then pass the verified `authInfo` to the handler. [MCP web-standard runtimes](https://ts.sdk.modelcontextprotocol.io/v2/serving/web-standard)
- The alternative Cloudflare Agents `createMcpHandler` is a stateless v2 wrapper for new Workers. It supplies route, CORS, hostname/origin allowlist, legacy-compatibility, response-mode, and subscription options. Its default legacy lane remains stateless: no persistent session ID, `GET`/`DELETE`, replay, or pushed server requests. [Cloudflare MCP handler API, updated 2026-10-18](https://developers.cloudflare.com/agents/model-context-protocol/apis/handler-api/)

### Streamable HTTP and authorization requirements

- A Streamable HTTP server **must** reject invalid present `Origin` headers with `403`; the specification also says servers should authenticate connections. Modern client POSTs carry `Accept: application/json, text/event-stream` and matching `MCP-Protocol-Version` header and body metadata; a mismatched or unsupported version is rejected with `400`. [MCP Streamable HTTP — security, message, and version rules](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)
- Authorization is optional for MCP generally, but an HTTP implementation that supports it should follow the MCP authorization specification. A protected MCP server is an OAuth 2.1 resource server and **must** implement RFC 9728 Protected Resource Metadata; it uses that metadata to direct clients to its authorization server. Bearer credentials are required on every HTTP request, must not be placed in the URL, and the resource server must validate the token and intended audience. [MCP Authorization — 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- The v2 SDK's Web-standard `requireBearerAuth` gate returns a ready OAuth challenge for absent/invalid/under-scoped tokens, and `oauthMetadataResponse` can publish the protected-resource and authorization-server metadata routes. Its verifier must populate expiry and resource/audience information; `expectedResource` rejects a token issued to another resource. Per-tool `scopeChallenge` can return `403 insufficient_scope` before invocation. [MCP SDK authorization guide](https://ts.sdk.modelcontextprotocol.io/v2/serving/authorization)
- Cloudflare documents four Worker authorization approaches: Cloudflare Access as OAuth provider, a third-party provider, an existing/own OAuth provider, or the Workers OAuth Provider library implementing the complete OAuth flow. The documentation explicitly supports mapping scopes/permissions to tools and conditionally exposing tools by permission. [Cloudflare MCP authorization, updated 2026-07-27](https://developers.cloudflare.com/agents/model-context-protocol/protocol/authorization/)

### Mutation-specific security

- MCP tools are model-controlled. The protocol recommends a human able to deny invocations, clear invocation indicators, and confirmation prompts; the protocol does not mandate one UI pattern. Tool annotations are untrusted unless the server is trusted. [MCP Tools — 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Every authorized request must be checked. A server must not treat possession of a routine/workflow/state handle as authentication; it should bind stored handles to the verified user identity and reject another principal's handle. [MCP security best practices — 2026-07-28](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)

A public MCP endpoint needs OAuth discovery, scoped authorization, expiry, and audience validation as above. |

## Recommendation — project decision, not protocol fact

1. **Add a separate, stateless `/mcp` Worker endpoint using `@modelcontextprotocol/server` v2.** Prefer the direct SDK handler if the project wants the smallest dependency surface; use Cloudflare Agents' `createMcpHandler` only if its built-in route/origin controls and OAuth integration are desired. In either case, pin package versions together and configure explicit production hostname and origin allowlists.
2. **Use a real OAuth 2.1 resource-server boundary from the first remote release.** For a single-user/private deployment, start with Cloudflare Access as the documented provider option; for multi-user LifeOS data, use the Workers OAuth Provider path (backed by the chosen identity provider) so the Worker can issue scoped MCP credentials and publish the required metadata. Derive the LifeOS account identity exclusively from the verified access token.
3. **Keep the MCP surface read-only** under `training:read` and `routines:read`. Provide bounded training summaries, exercise progress, routine review, and current training state; do not expose database access or routine mutations.
4. **Return evidence-backed observations rather than applying changes.** The AI can recommend routine adjustments in chat, while the user decides whether to edit the routine through the application.
5. **Treat synchronized workout check-ins as sensitive training context.** Scope every read to the verified subject, return only the data required for the requested analysis, and never accept a user/account ID from tool arguments as authority.
